
The performance audit identified these main bottleneck groups:

- `P-001`: naive mapmaking accumulates large `Eigen::Triplet` vectors, converts
  them to sparse matrices, then serially merges into dense maps.
- `P-002`: noise products allocate and traverse full
  `n_rows * n_cols * n_maps * n_noise` cubes.
- `P-003`: post-map diagnostics such as PSD, histogram, median error, and RMS
  are computed eagerly and can dominate noise-enabled reductions.
- `P-004`: jinc mapmaking has hot-loop kernel-footprint and validation costs.
- `P-005`: detector pointing and pixel-index work is recomputed in multiple
  places.

The user then asked whether the performance issues group into structural work.
The suggested grouping was:

  `P-003`.
- Diagnostic gating and output planning: `P-003`, parts of `P-009`.
- Pointing/index cache and mapmaker hot loops: `P-004`, `P-005`.
- IO/writer serialization: `P-006`.
- Cleaning/eigensolver benchmarks: `P-007`.

## New Map Accumulation Architecture Implemented So Far

The first implementation targets `P-001` only. It replaces the largest
sparse-triplet staging path in naive mapmaking with a tiled accumulator.

New helper:

```text
include/citlali/core/mapmaking/tiled_accumulator.h
```

The helper `mapmaking::TiledMapAccumulator`:

- Lazily allocates fixed-size dense tiles per map, default tile size 64.
- Uses a tile key lookup so repeated samples in the same map region accumulate
  directly into the same tile.
- Provides `reset(n_maps, n_rows, n_cols)`.
- Provides `add(map_index, row, col, value)`.
- Provides `merge_into(std::vector<Eigen::MatrixXd>& target)`.
- Throws on invalid map indices, invalid pixel indices, mismatched map counts,
  and mismatched target dimensions.

Changed mapmaking path:

```text
include/citlali/core/mapmaking/naive_mm.h
```

`NaiveMapmaker::populate_maps_naive()` now uses tiled accumulators for:

- OMB signal
- OMB weight
- OMB kernel
- OMB coverage
- CMB signal
- CMB weight
- CMB kernel
- CMB coverage

The previous local `std::vector<Eigen::Triplet<double>>` containers and
`Eigen::SparseMatrix` conversion helper were removed from this path.

Still unchanged:

- Noise accumulation still uses the existing full-cube scratch/merge path.
- Polarization pointing scratch matrices are still copied and merged as before.
- Jinc mapmaking is untouched.
- Maximum-likelihood mapmaking is untouched.
- Config and output file formats are untouched.

Expected scientific behavior:

- The mathematical accumulation target is unchanged for signal, weight, kernel,
  and coverage maps.
- Bitwise identity is not guaranteed because accumulation order may differ from
  Eigen sparse duplicate summation. Treat small floating-point differences as
  possible until checked against representative reductions.
- This should reduce allocation pressure and sparse-conversion overhead for
  standard naive mapmaking, especially for scan chunks that touch only a subset
  of the full map.

## Suggested Tolerance Strategy

For the first regression check:

- Expect exact equality for integer-like coverage contributions only if
  processing order and floating type behavior are unchanged.
- Use tight floating tolerances for signal, weight, and kernel maps rather than
  requiring bitwise identity.
- Report max absolute difference, max relative difference on nonzero pixels,
  RMS difference, and number of differing pixels.
- Separately inspect NaN/Inf counts and zero-weight pixels.
- Fail loudly on shape, WCS, unit, or metadata differences.

## Risks To Watch

- The tiled accumulator shifts duplicate-pixel summation from Eigen sparse
  assembly to direct additions in sample-loop order. This is scientifically
  reasonable but needs a regression comparison before treating the branch as
  production-safe.
- Tile size 64 is a pragmatic default, not tuned. It may need benchmarking
  across map sizes and scan footprints.
- The current implementation still merges each scan's tile buffers into global
  dense maps under `naive_mutex`. It reduces local staging and sparse conversion
  cost but does not remove all serial merge time.
- If a scan touches most of a large map, tile storage may approach dense scratch
  storage. This is still expected to be better than triplet staging for common
  repeated-hit patterns, but it should be measured.
- Noise maps are still the larger memory risk when `n_noise` is high. Do not
  interpret this branch as solving `P-002`.

## Recommended Path After Validation

If the `P-001` tiled accumulator validates numerically:

1. Keep it as a separate commit from later noise changes.
2. Add or enable focused tests for the accumulator through CMake.
3. Profile standard reductions with noise disabled and enabled.
4. Start `P-002` design from measured memory and wall-time data.

For `P-002`, the likely direction is not just another accumulator helper. The
better design question is how long noise cubes need to exist at full size and
which downstream products truly require all realizations in memory at once. A
good next architecture sketch should consider:

- a memory budget or preflight estimate for `n_rows * n_cols * n_maps * n_noise`,
- tiled or streamed accumulation of noise realizations,
- streaming empirical products where possible,
- gating expensive diagnostics unless requested by output configuration,
- preserving current output compatibility until a deliberate format change is
  chosen.
