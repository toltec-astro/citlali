### New Tool

- Tool:

  layout.
- Supports `--mode point`, `--mode beammap`, and `--mode science`.
- Compares matching FITS, netCDF, CSV, and ECSV products.
- Reports missing and extra comparable products.
- Ranks numeric array/column differences by max/median absolute and fractional
  difference.

- Skips logs, configs, `index.yaml`, `learning_iter_*.csv`, and
  `*_timestream.nc`.
- Use `--include-timestream` for deeper TOD diagnostics.
- Use `--include` and `--exclude` globs for targeted comparisons.
- Default numeric tolerance is aligned with the deterministic manifest wrapper:
  `--atol 2e-8 --rtol 1e-10`.

### How To Interpret Reports

- `Product Set Differences`:
  - Missing/extra products are often the first failure mode to inspect.
  - For beammap, missing final FITS/ECSV products are a hard validation concern
    unless the run was known to be incomplete.
- `Largest Numeric Differences`:
  - This table is useful for localizing differences by product and HDU/variable.
  - Small absolute changes with large fractional changes can occur where the
    baseline value is near zero; inspect `max_abs_diff` and `median_abs_diff`
    together.
- `Non-Tolerance Changes`:
  - These are the records outside `--atol/--rtol`, shape/header/product
    changes, or read errors.
  - A nonzero count is not automatically a regression, but it should be
    explained before continuing a risky refactor phase.

### Context

The user observed that Unity `cmake + build` is at least 6x slower than local
builds. The audit found that the normal Unity helper was paying the configure
cost on every update, and configure can invalidate a large part of the build
graph.

### Measured Local Timings

Measured in `/Users/gwilson/GitHub/citlali-refactor`:

- No-op build only:
  - `/usr/bin/time -p cmake --build build --target citlali_cli -j 8`
  - about `1.2 s`
- Configure only:
  - `/usr/bin/time -p cmake -S . -B build`
  - about `23 s`
- Build immediately after configure:
  - about `90 s`
- Configure with `-DFETCHCONTENT_UPDATES_DISCONNECTED=ON`:
  - about `22 s`
- Build immediately after that configure:
  - about `119 s`, including broad third-party dependency rebuilds

The key result is that the expensive path is not the build tool checking a
clean tree. The expensive path is explicitly running configure, then building.

### Likely Root Cause

- `tools/unity/citlali_refactor_bashrc.sh` previously always ran:
  - `cmake -S . -B build ...`
  - then `cmake --build build --target citlali_cli ...`
- `tula_cmake` generates `*_config/gitversion.h` during configure with a
  wall-clock timestamp.
- Those generated headers are included by broad headers such as `engine.h`,
  `kidsproc.h`, and CLI parsing.
- That makes configure invalidate PCH / the large CLI translation unit, and in
  some cases fetched dependency objects.
- A plain configure also tried to update `FetchContent` git checkouts, which
  creates network failure and latency risk.

Do not solve the header architecture issue in this workflow slice. That should
be part of the later "move non-template implementation out of headers" phase.

### Implemented Helper Behavior

`tools/unity/citlali_refactor_bashrc.sh` now defaults to:

1. fetch/switch/pull the refactor branch,
2. decide whether configure is actually needed,
3. skip explicit configure when the build tree is current,
4. run `cmake --build`.

New environment variable:

```bash
CITLALI_REFACTOR_CONFIGURE=auto    # default
CITLALI_REFACTOR_CONFIGURE=always  # force configure
CITLALI_REFACTOR_CONFIGURE=never   # fail instead of configuring
```

Auto mode runs configure when:

- `${build_dir}/CMakeCache.txt` is missing,
- `${build_dir}/CMakeFiles` is missing,
- CMake/dependency inputs changed between the pre-pull and post-pull commits,
- relevant cache options changed, including:
  - `CMAKE_BUILD_TYPE`
  - `CITLALI_USE_WIENER_FILTER_OMP`
  - `USE_INSTALLED_NETCDF`
  - `CONAN_CMD`
  - `FETCHCONTENT_SOURCE_DIR_TULA`
  - `FETCHCONTENT_UPDATES_DISCONNECTED`

The helper now adds this configure option whenever configure is run:

```bash
-DFETCHCONTENT_UPDATES_DISCONNECTED=ON
```

`tools/unity/unity.env.example` now documents
`CITLALI_REFACTOR_CONFIGURE`.

### Expected Unity Behavior

### Context

The first refactor beammap validation after the beammap helper extraction
segfaulted during split-by-flag FITS map output, immediately after:

```text
kernel_map_diag stage='map output ... split-by-flag before write'
output progress (flag=0) [  0%]
```

The focused fix changed the kernel FITS FWHM lookup in
`Engine::write_maps` from `calib.array_fwhms[calib.arrays(i)]` to
`calib.array_fwhms[array_index]`. In detector-grouped beammaps, `i` is a
detector/map index, not an index into the small `calib.arrays` vector. The
writer had already computed the correct map array identity through
`map_write_indices(...)`; the kernel FWHM path was simply not using it.

### Deferred Cleanup

The crash fix is intentionally narrow and should be the right behavior fix.
During a later output-writer refactor, clean up the surrounding naming and
guards so this class of bug is harder to reintroduce:

- Rename `MapWriteIndices::array_index` and local `array_index` variables to
  `array_id` or similar. The value is the TolTEC array id used to key
  `calib.array_fwhms`, not a positional index into `calib.arrays`.
- Add/centralize a checked array-FWHM lookup for FITS map output rather than
  indexing `calib.array_fwhms[...]` directly.
- Keep `map_write_indices(...)` as the single source of truth for
  map-index-to-output-file, Stokes, and array-id routing.
- Revisit this when splitting `Beammap::write_beammap_map_products` and the
  shared map image writer, not during the current beammap validation rerun.
