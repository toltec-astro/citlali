### Broad RTC Flagging Concern

The compact local RTC despike test still produced broad flagging in `redu10`:

- `rtc_despike_added_flagged_frac > 0.50`: `158` detector-scans
- `rtc_despike_added_flagged_frac > 0.90`: `40` detector-scans
- maximum added flagged fraction was about `0.998`

The key code candidate is in:

- `include/citlali/core/timestream/rtc/despike.h`
- `include/citlali/core/timestream/rtc/rtcproc.h`

Candidate logic issue:

- In `rtcproc.h`, the RTC despiker gets `window_size = filter.n_terms`.
- The FIR filter has `n_terms = 32` in the relevant config.
- In `despike.h`, compact local residual flags are expanded by
  `run_filter/window_size`.
- Therefore a compact local event can be padded by about `+/-32` samples.
- At the raw sample rate of about `122 Hz`, `32` samples is about `0.262 s`.
- At the relevant scan speed, that corresponds to about `12"` on one side, or
  roughly `25"` full width for a narrow trigger.

This explains why the user noticed that the flagged junk was about `32` samples
wide and also about `12"` in extent. The expansion may be appropriate for some
filter-transient use cases, but it is too broad for compact local event flags
if the trigger is not source-aware and not morphologically strict.

### Proposed Problem Split

Do not build one monolithic despiker to solve all of this. Split the problem
into at least three classifiers:

1. Detector-scan quality gate
   - Question: is this detector usable for this scan at all?
   - It should catch traces whose robust scatter/span are wildly unlike peers.
   - Output should be a detector-scan badness decision, not broad local sample
     flags.
   - First diagnostic metrics:
     - robust sigma ratio relative to same array/network peers,
     - robust `p99-p1` or `p99.5-p0.5` span ratio relative to peers,
     - fraction of samples already flagged,
     - extreme off-source excursion metrics.
   - Initial thresholds should be conservative because the obvious bad cases
     are huge, e.g. sigma ratio `>20` or span ratio `>50`, but only after
     handling source masking as described below.

2. Compact detector spike identifier/flagger
   - Question: does an otherwise usable detector have one or more narrow
     impulsive events?
   - Adjacent-difference paired-edge morphology is a promising basis.
   - It should require paired opposite-sign edges within a small number of raw
     samples and a return near the local baseline.
   - It should reject broad features, ramps, source-like crossings, and bad
     detector-scans.
   - It should apply only narrow local flags with modest padding. It should not
     inherit `window_size = filter.n_terms` expansion by default.

3. Network/scan event detector
   - Question: do many detectors or networks show aligned pathology?
   - This should be separate from single-detector compact spikes and from
     detector-scan badness.
   - Existing RTC network step/impulsive diagnostics may be the starting point,
     but policy should be reviewed separately.

### Source-Aware Detector-Scan Quality Gate

The detector-scan quality gate must avoid rejecting detectors merely because
they pass over bright 3C273. In a beammap we do not necessarily know the final
detector pointing yet, and the input APT is only a prior; it may also be missing
an entry for a detector.

Recommended source-mask ladder for quality-gate metrics:

1. Use final/working detector pointing if available.
2. Use input APT prior if that detector has a valid entry.
3. Use an array/network-level expected source-crossing window if the detector
   prior is missing.
4. If no source estimate exists, either run diagnostic-only or use extremely
   conservative thresholds; avoid hard rejection from source-contaminated
   samples.

For the first implementation, option 3 is important. Even without a valid
per-detector APT entry, the array/network source-crossing interval can be
estimated and padded generously. A broad source mask is better than a narrow
wrong one. The cost is fewer off-source samples; the benefit is not mistaking
3C273 for detector pathology.

Quality metrics should be computed on samples outside the source mask:

```text
quality_samples =
    all samples
    minus detector-prior source window if available
    minus network/array source-crossing window if available
    minus any robustly detected globally bright/common source interval
```

If too few off-source samples remain, the gate should abstain rather than make a
hard good/bad call.

### Current Interpretation

There are two distinct problems:

1. Broad RTC local flagging appears to be at least partly a logic/policy issue,
   likely involving expansion of compact local residual flags by the filter
   length. `scan 80 uid 4251` is the clearest example: the raw adjacent
   difference analysis found no compact spike, but the previous RTC diagnostics
   broadly flagged it.

2. Some detector-scans are intrinsically pathological in amplitude scale and
   shape. `uid 4250`, `uid 4251`, and `uid 1079` are not good templates for
   compact spike tuning. They should be handled by detector-scan quality logic
   before compact spike repair.

Both problems matter. We should avoid treating pathological traces as repairable
compact spikes, and we should avoid letting a compact trigger create a broad
source-scale mask.
