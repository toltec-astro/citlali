# TolTECA Reduction Mode Kits

These directories contain the versioned numbered-YAML authoring structures for
the four supported Citlali reduction modes. TolTECA still owns discovery and
merge of `NN_*.yaml`; Citlali still receives one generated low-level
configuration.

The checked files are generated from accepted Phase 4 validation snapshots.
Their identities are recorded in `manifest.yaml`. Do not hand-edit the
repository copies to change a baseline. Generate a successor kit from a named,
accepted low-level configuration and review the resulting policy-hash change.

The top-level `point/`, `oof/`, `beammap/`, and `science/` directories are the
mechanically exact V1 reference. They remain useful for policy archaeology and
compatibility checks, but are not the accepted operator interface: V1 exposes
too much implementation policy under generic filenames.

The canonical human-facing structure is V2 under `v2/`. It uses the same seven
mode-named roles for all four reductions, keeps the complete accepted policy in
a generated internal file, and limits ordinary editing to short runtime,
analysis-default, and product files. See [`v2/README.md`](v2/README.md).

## V1 Reference Roles

Every mode has the same five files:

| File | Purpose | Normal editor |
| --- | --- | --- |
| `70_pipeline.yaml` | Complete, repository-managed mode policy and Citlali step | Citlali maintainers |
| `71_runtime.yaml` | Executable, input root, output job key, thread policy, and deployment paths | Site or project setup |
| `72_observation.yaml` | Observation selection, APTs, calibrator fluxes, and pointing objects | TolPROJ or dataset owner |
| `80_products.yaml` | Standard output, coadd, noise-map, filtering, and fitting policy | Analysis owner |
| `90_user_overrides.yaml` | Small deliberate expert changes that must win by precedence | Analysis owner |

`40_setup.yaml` is generated by `tolteca setup` and is not part of these kits.
Diagnostic experiments should use named, temporary files above `80`; they
must not be accumulated into the standard kit silently.

The checked `72_observation.yaml` files contain obvious `OBSNUM` and APT
placeholders. They are structural examples, not runnable datasets. TolPROJ
replaces this file with project-specific observation and calibration records.

## Validate Repository Kits

From the Citlali repository root:

```bash
$HOME/tolteca/bin/python tools/config/tolteca_mode_kit.py validate-all
```

Strict validation checks:

- all five role files exist;
- numbered files merge with TolTECA/Tollan list-update semantics;
- the final reduction type matches the selected mode;
- every low-level leaf is in Citlali's checked config contract; and
- the normalized low-level policy matches the accepted manifest hash.

## Inspect A Deployed Project

The `merge` command allows an intentional policy change but still rejects
unknown leaves and a wrong reduction mode. It can emit the effective merged
YAML plus JSON or Markdown provenance reports:

```bash
$HOME/tolteca/bin/python tools/config/tolteca_mode_kit.py merge \
  --mode science \
  --mode-dir /path/to/reduction \
  --yaml-out /tmp/science-merged.yaml \
  --json-out /tmp/science-config-report.json \
  --markdown-out /tmp/science-config-report.md
```

The report names the final source file, authority domain, and typed owner for
each low-level value. Changes authored in `90_user_overrides.yaml` are also
listed separately. Use `validate --allow-policy-drift` for the same behavior
with validation-oriented naming; omit the flag to require the accepted hash.

## Regenerate A Successor

`tools/config/generate_tolteca_mode_kits.py` accepts one generated low-level
baseline and validation record ID per mode. It removes only TolTECA-generated
`inputs` and normalizes `runtime.output_dir` to `.` before hashing the policy.
The generator writes all five roles and a new manifest to a review directory.
Do not overwrite an accepted kit until the successor has passed the mode-kit
tests and mode-appropriate TolTECA reductions.

## TolPROJ Ownership

Citlali is the canonical source of these policies. TolPROJ vendors a versioned,
hash-checked snapshot and owns project instantiation on Unity: running
`tolteca setup`, copying the selected mode files, and generating the
mode-specific `72_MODE_observation.yaml` from project metadata. TolPROJ must
not import templates from a developer Citlali checkout at runtime.

The integration remains an explicit `--refactor` option. Without that option,
TolPROJ retains its established `70_reduce.yaml`/`72_reduce.yaml` behavior.
The refactor installer rejects mixed numbered-config families. On a same-kit
rerun it refreshes repository policy and generated observation metadata while
preserving the five operator-owned V2 files.
